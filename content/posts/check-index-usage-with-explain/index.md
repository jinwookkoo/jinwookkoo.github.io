관리자 페이지에서 데이터를 조회하는 과정에서 응답 속도가 예상보다 오래 걸리는 화면이 있었다. 원인을 확인하기 위해 쿼리를 살펴보던 중, 인덱스가 있음에도 실제 실행 계획에서는 이를 제대로 활용하지 않는 상황을 발견했다.

이 글에서는 `EXPLAIN`을 통해 쿼리가 인덱스를 사용하고 있는지 확인하는 방법을 정리해보려고 한다.

`EXPLAIN`은 MySQL 엔진이 쿼리를 어떻게 처리하는지에 대한 정보를 제공하는 실행 계획이라고 볼 수 있다. 최적의 쿼리를 실행하기 위해 <u>옵티마이저</u>가 어떤 접근 방식을 선택했는지 확인할 수 있으며, 이를 통해 인덱스 사용 여부나 예상 스캔 범위 등을 파악할 수 있다.

> **옵티마이저(Optimizer)**  
> 가장 효율적인 방법으로 SQL을 수행할 최적의 처리 경로를 생성해주는 DBMS의 핵심 엔진

실행 계획에 어떤 정보가 포함되는지 살펴보기 위해, 간단한 예시 테이블을 하나 기준으로 보려고 한다.

```text
mysql> DESCRIBE users;
+------------+---------------------+------+-----+-------------------+----------------+
| Field      | Type                | Null | Key | Default           | Extra          |
+------------+---------------------+------+-----+-------------------+----------------+
| id         | bigint(20) unsigned | NO   | PRI | NULL              | auto_increment |
| name       | varchar(20)         | NO   |     | NULL              |                |
| created_at | datetime            | NO   | MUL | CURRENT_TIMESTAMP |                |
+------------+---------------------+------+-----+-------------------+----------------+
```

이제 실행할 예시 쿼리에 `EXPLAIN`을 적용하면 다음과 같은 실행 계획을 확인할 수 있다.

```text
mysql> EXPLAIN SELECT * FROM users WHERE name = 'Alice';
+----+-------------+-------+------+---------------+------+---------+------+------+-------------+
| id | select_type | table | type | possible_keys | key  | key_len | ref  | rows | Extra       |
+----+-------------+-------+------+---------------+------+---------+------+------+-------------+
|  1 | SIMPLE      | users | ALL  | NULL          | NULL | NULL    | NULL |    5 | Using where |
+----+-------------+-------+------+---------------+------+---------+------+------+-------------+
```

| 항목 | 설명 |
|------|------|
| `id` | SELECT 문의 실행 순서를 나타내는 번호 |
| `select_type` | SELECT 문의 유형 |
| `table` | 접근하는 테이블 이름 |
| `type` | 테이블 데이터 접근 방식 |
| `possible_keys` | 사용할 수 있는 인덱스 목록 |
| `key` | 실제로 사용한 인덱스 |
| `key_len` | 사용한 인덱스의 길이 |
| `ref` | 인덱스 조회 시 기준이 되는 값 |
| `rows` | 조회 예상 행 수 |
| `Extra` | 실행 계획에 대한 추가 정보 |

인덱스 사용 여부를 확인할 때는 먼저 `possible_keys`와 `key`를 보면 된다. `possible_keys`는 사용할 가능성이 있는 인덱스 목록이고, `key`는 실제로 사용한 인덱스를 의미한다.

위 결과에서는 `possible_keys`와 `key`가 모두 `NULL`이므로, 이 쿼리는 인덱스를 사용하지 않은 상태라고 볼 수 있다. 또한 `type` 값이 `ALL`이기 때문에 테이블 전체를 순차적으로 읽는 전체 테이블 스캔 방식으로 처리되고 있음을 알 수 있다.

이번에는 인덱스가 설정된 `created_at` 컬럼을 기준으로 실행 계획을 다시 확인해보려고 한다.

```text
mysql> SHOW INDEX FROM users;
+-------+------------+----------------------+--------------+-------------+-----------+-------------+----------+--------+------+------------+---------+---------------+
| Table | Non_unique | Key_name             | Seq_in_index | Column_name | Collation | Cardinality | Sub_part | Packed | Null | Index_type | Comment | Index_comment |
+-------+------------+----------------------+--------------+-------------+-----------+-------------+----------+--------+------+------------+---------+---------------+
| users |          0 | PRIMARY              |            1 | id          | A         |           5 |     NULL | NULL   |      | BTREE      |         |               |
| users |          1 | idx_users_created_at |            1 | created_at  | A         |           5 |     NULL | NULL   |      | BTREE      |         |               |
+-------+------------+----------------------+--------------+-------------+-----------+-------------+----------+--------+------+------------+---------+---------------+
```

#### 조건절에서 함수를 사용한 경우
```text
mysql> EXPLAIN SELECT * FROM users WHERE DATE_FORMAT('created_at', '%Y-%m-%d') = '2022-04-26';
+----+-------------+-------+------+---------------+------+---------+------+------+------------------+
| id | select_type | table | type | possible_keys | key  | key_len | ref  | rows | Extra            |
+----+-------------+-------+------+---------------+------+---------+------+------+------------------+
|  1 | SIMPLE      | NULL  | NULL | NULL          | NULL | NULL    | NULL | NULL | Impossible WHERE |
+----+-------------+-------+------+---------------+------+---------+------+------+------------------+
```
`created_at` 컬럼에 인덱스가 설정되어 있어도, 조건절에서 `DATE_FORMAT()` 함수를 사용하면 실행 계획에서는 인덱스를 활용하지 못할 수 있다.
위 결과에서도 `possible_keys`와 `key`가 모두 `NULL`이고 `type` 값이 `ALL`이므로, 인덱스를 사용하지 않은 채 전체 테이블 스캔으로 처리되고 있음을 확인할 수 있다.
문제가 되는 페이지에서 확인한 느린 조회 쿼리 역시 이와 비슷하게 조건절에서 MySQL 함수를 사용하고 있었다.

#### 조건절에서 함수를 사용하지 않은 경우
```text
mysql> EXPLAIN SELECT * FROM users WHERE created_at >= '2022-04-26 00:00:00' AND created_at < '2022-04-27 00:00:00';
+----+-------------+-------+-------+----------------------+----------------------+---------+------+------+-----------------------+
| id | select_type | table | type  | possible_keys        | key                  | key_len | ref  | rows | Extra                 |
+----+-------------+-------+-------+----------------------+----------------------+---------+------+------+-----------------------+
|  1 | SIMPLE      | users | range | idx_users_created_at | idx_users_created_at | 5       | NULL |    1 | Using index condition |
+----+-------------+-------+-------+----------------------+----------------------+---------+------+------+-----------------------+
```

이번 결과에서는 `possible_keys`와 `key`에 모두 `idx_users_created_at`이 표시되고 있다. 즉, `created_at` 컬럼에 설정된 인덱스를 실제 실행에 사용하고 있다는 의미이다.

또한 `type` 값이 `range`로 나타나므로, 전체 테이블을 순차적으로 읽는 것이 아니라 조건에 맞는 범위를 기준으로 인덱스를 탐색하고 있음을 알 수 있다.

이 외에도 컬럼에 연산을 사용하거나 `LIKE '%keyword'`처럼 앞부분에 와일드카드를 사용한 경우 등에는 인덱스를 효율적으로 활용하지 못할 수 있다.

인덱스가 존재한다고 해서 항상 사용되는 것은 아니기 때문에, 쿼리를 작성하거나 수정한 뒤에는 `EXPLAIN`을 통해 실제 실행 계획을 함께 확인하는 것이 중요하다.
